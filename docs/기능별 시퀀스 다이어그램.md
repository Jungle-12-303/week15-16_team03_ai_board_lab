# 전체 기능 시퀀스 다이어그램

분석 기준: `frontend/src/App.jsx`, `frontend/src/api/client.js`, `backend/src/main/java`, `backend/src/main/resources/db/migration/V1__init.sql`, `docker-compose.yml`, `infra/nginx/default.conf`를 기준으로 확인했다.

## 확인됨 / 설계 해석

- 확인됨: Frontend API 호출은 `client.js`의 `authApi`, `postApi`, `aiApi`를 통해 이뤄진다.
- 확인됨: 인증이 필요한 요청은 Axios interceptor가 `localStorage.token`을 `Authorization: Bearer ...`로 붙인다.
- 확인됨: Backend의 일반 기능은 `Controller -> Service -> Repository -> DB` 흐름이다.
- 확인됨: RAG 기능은 `RagService -> OpenAiClient -> JdbcTemplate -> post_embeddings` 흐름이다.
- 확인됨: MCP 기능은 `McpService -> GitHub API -> mcp_tool_logs` 흐름이다.
- 확인됨: Agent 기능은 `AgentService`가 RAG, MCP, OpenAI, memory/log 저장을 조합한다.
- 설계 해석: 이 문서는 “사용자 기능 단위”로 시퀀스를 나눴다. 이유는 초보자가 다시 구현할 때 API endpoint 단위보다 사용자가 누르는 버튼/행동 단위가 더 기억하기 쉽기 때문이다.

```txt

2. 회원가입
3. 로그인
4. 로그아웃
5. 게시글 목록/검색/페이징

13. RAG 유사 글 검색/요약
```

### 왜 이 순서인가

사용자가 실제로 앱을 쓰는 순서와 백엔드 내부 기능 의존 순서를 같이 반영했다. 예를 들어 게시글 작성은 인증, 태그 처리, 게시글 저장, RAG 인덱싱을 모두 포함하므로 단순 CRUD보다 뒤쪽에 AI 자동 인덱싱 흐름을 따로 분리했다.

## 1. 앱 실행 / 초기 목록 조회

```mermaid
sequenceDiagram

    App->>App: useEffect 실행

    Service->>Service: normalizeNullable(keyword/tag)
```

### 왜 이 흐름인가

초기 화면은 사용자가 아무 버튼을 누르지 않아도 게시판 목록을 보여줘야 한다. 그래서 `useEffect`에서 `loadPosts(0)`를 실행한다. 목록 응답은 상세 본문 전체가 아니라 `PostSummaryResponse`를 사용해 미리보기와 댓글 수만 내려준다.

## 2. 회원가입

```mermaid
sequenceDiagram
    participant User as 사용자
    participant AuthPanel
    participant Client as authApi
    participant Controller as AuthController
    participant Service as AuthService
    participant Repo as UserRepository
    participant Encoder as PasswordEncoder
    participant Jwt as JwtTokenProvider
    participant DB as users

    User->>AuthPanel: email/nickname/password 입력
    AuthPanel->>AuthPanel: submit(event)
    AuthPanel->>Client: authApi.signup(form)
    Client->>Controller: POST /api/auth/signup
    Controller->>Service: signup(SignupRequest)
    Service->>Service: email trim + lower-case
    Service->>Repo: existsByEmail(email)
    Repo->>DB: email 중복 조회
    DB-->>Repo: exists 여부
    alt 이미 가입된 이메일
        Service-->>Controller: IllegalArgumentException
    else 가입 가능
        Service->>Encoder: encode(password)
        Encoder-->>Service: passwordHash
        Service->>Repo: save(new UserEntity(...))
        Repo->>DB: users insert
        DB-->>Repo: saved user
        Service->>Jwt: createToken(userId,email)
        Jwt-->>Service: JWT
        Service-->>Controller: AuthResponse
        Controller-->>Client: JSON
        Client-->>AuthPanel: data
        AuthPanel->>AuthPanel: localStorage token/user 저장
        AuthPanel->>AuthPanel: setUser, setNotice
    end
```

### 왜 이 흐름인가

회원가입 직후 바로 로그인 상태로 만들기 위해 `AuthService.signup()`도 `AuthResponse`와 JWT를 반환한다. 비밀번호는 평문 저장하면 안 되기 때문에 `PasswordEncoder.encode()`를 거쳐 `password_hash`로 저장한다.

```mermaid
            Service-->>Controller: AuthResponse
            Controller-->>Client: JSON
            Client-->>AuthPanel: data
            AuthPanel->>AuthPanel: localStorage token/user 저장
            AuthPanel->>AuthPanel: setUser, setNotice
        end
    end
```

### 왜 이 흐름인가

로그인은 DB의 비밀번호 해시와 사용자가 입력한 비밀번호를 비교하는 과정이다. JWT는 서버 세션을 만들지 않고도 이후 요청에서 사용자를 증명하게 해준다.

## 7. 게시글 작성

```mermaid
sequenceDiagram
    participant User as 사용자
    participant Editor as PostEditor
    participant App as App.jsx
    participant Client as postApi
    participant Axios as Axios interceptor
    participant Filter as JwtAuthenticationFilter
    participant Controller as PostController
    participant Service as PostService
    participant CurrentUser as CurrentUserService
    participant TagService
    participant Repo as PostRepository
    participant Rag as RagService
    participant DB as PostgreSQL

    User->>Editor: 제목/본문/태그 입력 후 저장
    Editor->>App: onSubmit(savePost)
    App->>App: editor.tags 문자열을 List<String>으로 변환
    App->>Client: postApi.create(payload)
    Client->>Axios: POST /posts
    Axios->>Axios: localStorage.token을 Authorization에 삽입
    Axios->>Filter: POST /api/posts
    Filter->>Filter: JWT 검증 후 SecurityContext 설정
    Filter->>Controller: 요청 전달
    Controller->>Service: create(PostRequest)
    Service->>CurrentUser: getCurrentUser()
    CurrentUser-->>Service: UserEntity
    Service->>TagService: getOrCreateTags(request.tags)
    TagService->>DB: tags 조회/생성

    Repo->>DB: posts/post_tags insert
    DB-->>Repo: saved post
    Service->>Rag: indexPostSafely(post)
    Rag->>DB: post_embeddings upsert 시도
    Service->>Service: toDetail(post)
    Service-->>Controller: PostDetailResponse
    Controller-->>Client: JSON
    Client-->>App: saved
    App->>App: loadPosts(0), loadPost(saved.id)
```

### 왜 이 흐름인가

게시글 작성은 “저장” 하나로 보이지만 실제로는 인증 사용자 확인, 태그 정규화, 게시글 저장, RAG 인덱싱, 상세 응답 생성이 순서대로 일어난다. 이 순서를 `PostService.create()`에 모아야 기능의 트랜잭션 경계가 분명해진다.

```mermaid
    Service->>CurrentUser: getCurrentUser()
    Service->>Repo: findById(id)
    Repo->>DB: posts select
    Service->>Service: verifyOwner(post,user)
    alt 작성자가 아님

        Rag->>DB: post_embeddings upsert 시도
        Service->>Service: toDetail(post)
        Service-->>Controller: PostDetailResponse
        Controller-->>Client: JSON
        Client-->>App: saved
        App->>App: loadPosts(0), loadPost(saved.id)
    end
```

### 왜 이 흐름인가

수정은 작성과 달리 “소유권 검증”이 핵심이다. `verifyOwner()`를 통과한 뒤에만 엔티티를 변경하고 RAG 인덱스를 갱신한다.

## 9. 게시글 삭제

```mermaid
sequenceDiagram
    participant User as 사용자
    participant Detail as PostDetail
    participant App as App.jsx
    participant Client as postApi
    participant Filter as JwtAuthenticationFilter
    participant Controller as PostController
    participant Service as PostService
    participant CurrentUser as CurrentUserService
    participant Repo as PostRepository
    participant DB as PostgreSQL

    User->>Detail: 삭제 버튼 클릭
    Detail->>App: deletePost(post.id)
    App->>User: confirm("게시글을 삭제할까요?")
    alt 취소
        App-->>Detail: 아무 작업 없음
    else 확인
        App->>Client: postApi.remove(id)
        Client->>Filter: DELETE /api/posts/{id} + Bearer
        Filter->>Controller: 인증 후 요청 전달
        Controller->>Service: delete(id)
        Service->>CurrentUser: getCurrentUser()
        Service->>Repo: findById(id)
        Repo->>DB: posts select
        Service->>Service: verifyOwner(post,user)
        alt 작성자가 아님
            Service-->>Controller: AccessDeniedException
        else 작성자임
            Service->>Repo: delete(post)
            Repo->>DB: posts delete
            DB->>DB: comments/post_tags/post_embeddings cascade delete
            Service-->>Controller: void
            Controller-->>Client: 204 No Content
            Client-->>App: 완료
            App->>App: selectedPost=null, mode="list", loadPosts(0)
        end
    end
```

### 왜 이 흐름인가

삭제도 수정처럼 소유권 검증이 필요하다. DB migration에서 comments, post_tags, post_embeddings는 `ON DELETE CASCADE`이므로 게시글 삭제 시 관련 데이터도 같이 정리된다.

## 12. RAG 자동 인덱싱

```mermaid
sequenceDiagram
    participant PostService
    participant Rag as RagService
    participant OpenAI as OpenAiClient
    participant External as OpenAI API
    participant DB as post_embeddings
    participant Log as AiLogService

    PostService->>Rag: indexPostSafely(post) 내부에서 indexPost(post)
    Rag->>Rag: sourceText = title + "\\n" + content
    Rag->>OpenAI: createEmbedding(sourceText)
    alt OPENAI_API_KEY 없음 또는 API 실패
        OpenAI->>OpenAI: createLocalEmbedding(text)
        OpenAI-->>Rag: local vector
    else API 호출 성공
        OpenAI->>External: POST /v1/embeddings
        External-->>OpenAI: embedding
        OpenAI-->>Rag: vector
    end
    Rag->>OpenAI: toVectorLiteral(vector)
    OpenAI-->>Rag: "[...]" vector literal
    Rag->>DB: insert ... on conflict(post_id) do update
    alt upsert 성공
        Rag->>Log: log("RAG_INDEX", sourceText, "postId=...", true, null)
    else upsert 실패
        Rag->>Log: log("RAG_INDEX", sourceText, null, false, error)
        Rag-->>PostService: 예외 throw
        PostService->>PostService: 예외 무시, 게시글 저장 유지
    end
```

### 왜 이 흐름인가

RAG 검색은 게시글이 저장될 때 embedding이 만들어져 있어야 빠르게 동작한다. 하지만 AI 인덱싱 실패가 게시글 CRUD를 막으면 기본 게시판 기능이 깨지므로 `indexPostSafely()`가 보호막 역할을 한다.

## 17. JWT 인증 공통 흐름

```mermaid
sequenceDiagram

    participant Filter as JwtAuthenticationFilter
    participant Jwt as JwtTokenProvider
    participant UserRepo as UserRepository
```

## [2] 설계 이유 (WHY 중심)

### 왜 기능별 시퀀스로 나눴는가

하나의 거대한 시퀀스 다이어그램에 모든 기능을 넣으면 선이 너무 많아져서 학습용으로 보기 어렵다. 이 프로젝트는 기능이 Controller endpoint 단위로 명확히 나뉘므로, 사용자 행동 단위로 분리하는 것이 다시 구현할 때 더 유리하다.

### 왜 공통 흐름을 따로 뺐는가

JWT 인증과 예외 처리는 거의 모든 API에 반복해서 적용된다. 각 기능 다이어그램에 매번 전체 인증/예외 처리를 자세히 넣으면 핵심 기능 흐름이 흐려진다. 그래서 기능별 다이어그램에는 인증을 짧게 표시하고, 공통 인증/예외 흐름은 별도 다이어그램으로 분리했다.

### 왜 RAG 인덱싱과 RAG 검색을 분리했는가

인덱싱은 게시글 작성/수정 후 자동으로 일어나는 “저장 준비” 흐름이고, 검색은 사용자가 AI 버튼을 눌렀을 때 일어나는 “조회” 흐름이다. 두 기능이 모두 `RagService`에 있지만 실행 시점과 목적이 다르기 때문에 분리했다.

## [4] 중요한 포인트 정리

### 핵심 개념

- 시퀀스 다이어그램은 “시간 순서”를 보여준다.
- `Controller -> Service -> Repository`는 요청 처리의 기본 뼈대다.
- `JwtAuthenticationFilter`는 Controller 전에 실행된다.
- `CurrentUserService`는 Service에서 현재 로그인 사용자를 꺼내기 위한 도우미다.
- RAG는 인덱싱과 검색이 분리되어 있다.
- MCP는 JSON-RPC request를 외부 API 호출로 바꾸는 어댑터다.
- Agent는 도구 선택, 도구 실행, 결과 조합, memory/log 저장을 한 번에 처리한다.

### 헷갈리기 쉬운 부분

- `savePost()`는 작성과 수정을 모두 처리한다. `editingId`가 있으면 update, 없으면 create다.
- `runSimilar()`는 상세 화면에서는 `selectedPost`, 작성 화면에서는 `editor` 내용을 query로 사용한다.
- `github.getRepo`는 백엔드에서 지원하지만 현재 UI 버튼은 `github.getUser`만 호출한다.
- RAG 인덱싱 실패는 게시글 저장 실패와 같지 않다. `indexPostSafely()`가 예외를 삼킨다.
- OpenAI 키가 없어도 embedding/chat은 fallback으로 동작한다.

### 실수하기 쉬운 부분

- 인증이 필요한 API에서 token이 없으면 `CurrentUserService.getCurrentUser()` 단계에서 실패한다.
- 태그는 프론트에서는 comma string이지만 백엔드에서는 `List<String>`이다.
- `post_embeddings.vector(1536)`과 `app.ai.embedding-dimensions`가 맞아야 한다.
- Agent의 도구 실행은 최대 3회라서 도구를 더 추가하면 우선순위와 제한도 같이 봐야 한다.
- Nginx 배포에서는 `/api` prefix가 backend로 전달되는 구조를 유지해야 한다.
