# Project Alpha RAG 측정 로그 인벤토리

이 문서는 Project Alpha에서 실제로 남아 있는 RAG 관련 점수 측정값을 출처별로 모은 것이다.

주의할 점은 모든 표를 하나의 순위표처럼 비교하면 안 된다는 점이다. `scripts/evaluate-rag-retrieval.mjs`의 6케이스 평가, Spring 내부 `rag-evaluation-k5.json`의 5케이스 평가, RAGAS의 5케이스 생성 품질 평가는 서로 평가셋과 기준이 다르다.

이 문서에서 사용하는 평가 구분은 다음과 같다.

| 구분 | 의미 | 읽는 방법 |
|---|---|---|
| 오프라인 실험 | 서버를 띄우지 않고 DB/저장된 임베딩/스크립트 계산으로 후보를 비교한 실험 | 후보 선별용이며 채택 전 온라인 검증을 거친다. |
| 온라인 실험 | 실제 Spring API를 띄우고 OpenAI, Qdrant, MySQL, 서버 랭킹 경로를 모두 태운 실험 | 현재 서비스 동작에 가장 가까운 정량 근거다. |
| 과거 온라인 기록 | 과거 코드 상태에서 실제 API로 측정했지만 현재 구조와 검색 경로가 달라진 기록 | 개선 흐름 설명용이다. 현재 후보와 숫자만 직접 비교하지 않는다. |
| 시나리오 입출력 평가 | 실제 입력을 넣고 추천 제목/초안 일부를 사람이 읽어보는 평가 | 정량 점수의 보조 근거다. |

## 4. 온라인 후보 검증 JSON

출처: `backend/build/rag-online-candidate-evaluation.json`

이 평가는 후보 설정마다 Spring Boot 서버를 임시 포트로 실행하고 `/api/ai/similar-posts`를 호출했다. 따라서 Qdrant 벡터 검색, MySQL 원본 조회, OpenAI 쿼리 임베딩, 서버 내부 랭킹 로직이 모두 포함된 온라인 검증이다.

| 후보 | Cases | Hit@5 | Recall@5 | Precision@5 | MRR@5 | NDCG@5 | 판단 |
|---|---:|---:|---:|---:|---:|---:|---|
| Current baseline | 6 | 1.0000 | 0.4621 | 0.8000 | 1.0000 | 0.8599 | 기준선 |
| Query title + content | 6 | 1.0000 | 0.4725 | 0.8333 | 1.0000 | 0.9037 | 단독 개선 |
| Chunk evidence 3% | 6 | 1.0000 | 0.4621 | 0.8000 | 1.0000 | 0.8624 | 소폭 개선 |
| BM25 k1=2 b=0.25 | 6 | 1.0000 | 0.4534 | 0.8000 | 1.0000 | 0.8550 | 단독 악화 |
| Query terms 12 / guard 6 | 6 | 1.0000 | 0.4758 | 0.8333 | 1.0000 | 0.9014 | 단독 개선 |
| Weighted fusion | 6 | 1.0000 | 0.3565 | 0.6000 | 1.0000 | 0.6898 | 폐기 |
| Combined tuned | 6 | 1.0000 | 0.4957 | 0.8667 | 1.0000 | 0.9076 | 최종 채택 |
| Combined tuned + weighted fusion | 6 | 1.0000 | 0.3843 | 0.6333 | 1.0000 | 0.7116 | 폐기 |
| Metadata off diagnostic | 6 | 1.0000 | 0.4621 | 0.8000 | 1.0000 | 0.8599 | 채택 안 함 |

이 결과를 기준으로 기본 운영 설정은 `Combined tuned`로 조정했다. `Weighted fusion`은 오프라인/내부 ablation에서 점수가 높았지만 실제 API 경로에서는 크게 악화되어 폐기했다.

오프라인 실험은 후보 선별 도구로 사용했다. 실제로 `BM25 k1=2 b=0.25`는 오프라인에서는 높은 점수를 기록했지만 온라인 단일 변경에서는 `NDCG@5 0.8599 -> 0.8550`으로 내려갔다. `Metadata off`도 오프라인 점수는 높았지만 온라인에서는 기준선과 같았고, 사용자 카테고리/태그 맥락을 무시하므로 채택하지 않았다. 반대로 `Title + content`, `Query terms 12 / guard 6`은 오프라인 가설이 온라인에서도 유지됐다.

오프라인과 온라인의 가장 큰 차이는 후보군이 만들어지는 위치다. 오프라인은 MySQL에 저장된 게시글/청크를 넓게 읽고 JS 스크립트가 직접 BM25/vector/RRF 점수를 계산한다. 온라인은 실제 서비스처럼 Qdrant가 먼저 후보 `postId`를 자르고, 그 후보만 MySQL에서 조회한 뒤 Java `SimilarPostSearchService`가 metadata 완화, BM25, RRF, keyword, chunk evidence를 적용한다. 따라서 온라인에서 Qdrant 1차 후보에 들어오지 못한 글은 BM25 점수가 좋아도 뒤에서 복구되지 않는다. 이 때문에 오프라인에서 높은 점수를 기록한 BM25 파라미터나 metadata 설정이 온라인에서는 다른 결과를 낸다.

따라서 발표에서는 "오프라인 점수가 높은 후보를 바로 적용했다"가 아니라 "오프라인으로 후보를 줄이고, 온라인 API 경로에서 다시 검증해 최종 채택했다"라고 설명한다.

채택 설정을 `application.properties` 기본값으로 반영한 뒤 `scripts/evaluate-rag-retrieval.mjs`를 다시 실행했고, 결과는 `backend/build/rag-current-retrieval-evaluation.json`에 저장했다.

`0.99 cutoff 실험`은 커밋 `b2e013e tune: 유사글 표시 점수 0.99 미만 제외`에서 도입됐다. 사용자 화면에서 높은 표시 점수의 결과가 제목상 맞지 않아 보였고, 처음에는 최종 score를 강하게 자르는 방식으로 접근했다. 하지만 평가 결과가 급락하고 여러 케이스가 빈 결과가 되면서, 이후 방향은 score cutoff 중심이 아니라 실제 입력/출력 제목, 핵심어, metadata를 함께 확인하는 방식으로 바뀌었다.

`짧은 쿼리 최종 튜닝`의 `NDCG@5 0.9365`는 오프라인 값은 아니지만, 현재 최종 코드와 같은 조건에서 나온 후보 검증 결과도 아니다. 이후 Nori, Qdrant, 검색 설정 파라미터화가 들어가며 검색 경로가 바뀌었기 때문에 현재 최종 채택안과 숫자만 직접 비교하지 않는다. 현재 구조 안에서의 비교 기준선은 `Nori/Qdrant 현재 재검사`의 `NDCG@5 0.8599`이고, 최종 설정 재측정값은 `NDCG@5 0.9076`이다.

## 8. 중복과 제외 기준

중복으로 본 것:

- 같은 코드 상태에서 재실행되어 완전히 같은 평균값이 나온 행
- `docs/rag-performance-report.md`를 읽으면서 과거 표가 다시 출력된 행
- `backend/build/nori-rag-eval.out.log`를 여러 번 `Get-Content`한 행

별도 보관하되 공식 평균 지표에는 섞지 않은 것:

- `/api/ai/similar-posts`를 단건 호출했을 때 나온 개별 게시글 `score`
- 단건 호출의 `elapsed=30.858737` 같은 응답 시간 측정
- 프론트 화면에서 보인 유사글 score

이 값들은 디버깅에는 유용하지만 `Precision@5`, `Recall@5`, `MRR@5`, `NDCG@5`, `Hit@5`와 같은 평가 지표와 성격이 다르다.

## 9. 발표용으로 쓸 때의 결론

발표나 팀 공유에서는 아래 세 줄로 정리하는 것이 가장 안전하다.

1. 초기 vector 중심 검색은 `Precision@5 0.7000`, `NDCG@5 0.7370` 수준이었다.
2. BM25, metadata, RRF를 섞은 hybrid 검색에서 `Precision@5 0.9333`, `NDCG@5 0.9538`까지 오른 실험 흐름이 있었다.
3. 최신 온라인 후보 검증에서는 `Combined tuned`가 `Precision@5 0.8667`, `NDCG@5 0.9076`, `MRR@5 1.0000`, `Hit@5 1.0000`으로 가장 좋아 최종 설정으로 채택했다.
